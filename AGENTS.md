# Agent Guidelines

## Repository Purpose

`local-infrastructure` provides shared local development services. It is not an application and must remain independent of application-specific products, organizations, repositories, or technology stacks.

Application repositories belong in `repositorios/`. They keep their own Git history, dependencies, environment files, test commands, and runtime instructions.

## Local Services

The root `docker-compose.yml` provides only these shared services:

- RabbitMQ
- MongoDB
- Mongo Express
- MinIO
- Mailpit
- Portainer

Do not add application containers, application build contexts, product-specific queues, buckets, CORS rules, credentials, API paths, or lifecycle policies to the root Compose file. An application that needs Docker should keep its Compose configuration in its own repository and join the shared network when necessary.

## Repository Conventions

- Use `repositorios/` for cloned application repositories. Never treat them as Git submodules.
- Keep local secrets in `.env`. It is ignored by Git and generated by `setup-local.sh`.
- Keep `.env.example` free of working credentials, secrets, tokens, and private URLs.
- Preserve LF line endings for shell scripts and Compose files so they work in both WSL and Linux.
- Use `bash ./setup-local.sh` and `bash ./update-local.sh`; do not require a PowerShell-specific workflow.
- On Windows, run Docker Engine and Docker Compose inside the target WSL distribution; do not depend on a Windows-hosted container runtime.

## Change Guidelines

- Prefer small, generic changes that work for applications built with different technologies.
- Do not hardcode application repository URLs, branch names, package managers, service names, ports, build contexts, or framework commands.
- `setup-local.sh` may provision only host prerequisites required by this repository: Git, Docker Engine, and Docker Compose. Do not install application dependencies; each application owns its bootstrap process.
- Document a feature only after it is implemented in this repository.
- Update `README.md`, `README.en.md`, and relevant files in `docs/` when changing infrastructure behavior.

## Validation

After changing shell scripts, run:

```bash
bash -n setup-local.sh
bash -n update-local.sh
```

When Docker is available, validate Compose before starting services:

```bash
docker compose config
docker compose up -d
docker compose ps
```

Do not expose generated `.env` values in command output, documentation, commits, or pull requests.
